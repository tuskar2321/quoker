# 02. Архитектура

## Обзор

```
 Телефон (РФ)                Ядро · VPS в РФ                     Воркер · VPS за рубежом
┌───────────┐  HTTPS   ┌──────────────────────────┐   mTLS gRPC   ┌──────────────────────┐
│ Android   │ ───────▶ │ Caddy :443 (api / w)     │ ◀──────────── │ worker               │
│ app       │          │ core: REST API, gRPC,    │  (воркер сам  │ yt-dlp, ffmpeg,      │──▶ TikTok / Instagram
└───────────┘          │ SQLite, очередь, кэш mp4 │   подключается)│ Telegram-клиент      │──▶ Telegram Bot API
                       └──────────────────────────┘               └──────────────────────┘
```

Два сервиса на Go:

- **Ядро (core)** — на постоянном сервере в РФ. Единственная точка входа для приложения. Хранит всё состояние: пользователей, сессии, привязки, цели, историю, очередь задач, кэш файлов, конфиг воркеров (включая токен бота и cookies Instagram). Само никогда не ходит за рубеж.
- **Воркер (worker)** — stateless, на заменяемом зарубежном VPS. Подключается к ядру, получает конфиг и задачи, ходит в TikTok, Instagram и Telegram. Временные файлы — только в `/tmp`.

## Почему так

| Решение | Причина |
| --- | --- |
| Телефон ходит только на российский IP | Соединения с мобильных сетей РФ на зарубежные хостинги нестабильны; видео — это мегабайты |
| Всё состояние в ядре | Ядро надёжно, под угрозой только IP-блокировка воркера; воркер должен быть одноразовым |
| Соединение открывает воркер | Ядро не инициирует трафик за рубеж и не знает адрес воркера; при блокировке воркер переезжает без изменений ядра |
| Обычный TLS 1.3 + mTLS вместо VPN-протокола | Такой трафик неотличим от интеграции с зарубежным API; VPN-протоколы фильтруются по сигнатурам |
| REALITY только как запасной транспорт | Включается переменной на воркере, если прямой TLS начнут резать |
| Бот выполняет воркер, решения принимает ядро | Telegram доступен только из-за рубежа; логика привязок и прав должна жить рядом с данными |
| Отправка в Telegram с воркера | Файл уже на воркере; гонять его через ядро и обратно бессмысленно |

## Компоненты ядра

| Пакет | Ответственность |
| --- | --- |
| `internal/core/httpapi` | REST API для приложения (`docs/03-public-api.md`), аутентификация по сессии, rate limit |
| `internal/core/link` | gRPC-сервер для воркеров (`docs/04-core-worker-protocol.md`), реестр подключений, выдача задач |
| `internal/core/files` | Приём файлов от воркеров (`PUT /internal/v1/...`), кэш mp4 и обложек, LRU-вытеснение, Range-раздача |
| `internal/core/queue` | Очередь задач на SQLite: аренда, таймауты, повторы, отмена |
| `internal/core/videos` | Резолв, дедупликация по `video_id`, состояние файла |
| `internal/core/sends` | Отправки: проверка доступа, сбор подписи, статусы |
| `internal/core/bot` | Обработка апдейтов Telegram от воркера: `/start`, `my_chat_member`, `/connect`, админ-команды; исходящие сообщения бота как задачи `bot_call` |
| `internal/core/accounts` | Пользователи, инвайты, сессии, привязка Telegram |
| `internal/core/targets` | Реестр целей и проверки прав |
| `internal/core/admin` | Статус системы, алерты, ежедневная сводка |
| `internal/core/store` | SQLite, миграции, транзакции |
| `internal/shared/urls` | Извлечение и нормализация ссылок (используется и ядром, и для генерации тестовых векторов клиенту) |

## Компоненты воркера

| Пакет | Ответственность |
| --- | --- |
| `internal/worker/link` | Клиент gRPC-стрима: подключение, переподключение с backoff, heartbeat |
| `internal/worker/runner` | Исполнение задач с ограничением параллельности (по умолчанию 2) и отменой |
| `internal/worker/ytdlp` | Запуск yt-dlp как внешнего процесса с таймаутом, парсинг JSON, выбор формата |
| `internal/worker/telegram` | Клиент Bot API: `getUpdates` (если воркер — опрашивающий), `sendVideo`, произвольные вызовы для `bot_call` |
| `internal/worker/upload` | Заливка файлов и обложек в ядро с докачкой |
| `internal/worker/tmpcache` | Локальный LRU временных файлов (до 1 ГБ), чтобы отправка после скачивания не качала заново |

## Ключевые потоки

### Резолв

1. Приложение → `POST /v1/videos/resolve {url}`.
2. Ядро нормализует ссылку. Если `video_id` вычисляется без сети и видео в кэше — сразу `200`.
3. Иначе ставит задачу `resolve` и ждёт результат до 15 с; дождалось — `200 {video}`, нет — `202 {task_id}` и клиент опрашивает `GET /v1/tasks/{id}`.
4. Воркер: `yt-dlp -J` (с cookies для Instagram при отказе), качает обложку, заливает её в ядро, возвращает метаданные.

### Скачивание на телефон

1. Приложение → `POST /v1/videos/{id}/prepare`. Файл есть в кэше ядра → `200 {ready}`; нет → задача `download`, `202 {task_id}`.
2. Воркер качает лучший формат (для TikTok — без водяного знака), заливает в ядро, оставляет копию в своём tmp-кэше.
3. Приложение качает `GET /v1/videos/{id}/file` с Range, сохраняет в MediaStore, сообщает `POST /v1/videos/{id}/downloaded`.

### Отправка

1. Приложение → `POST /v1/sends {video_id, target_id, caption, sign}`.
2. Ядро проверяет: цель принадлежит пользователю и активна; пользователь всё ещё имеет права в чате (кэш 5 мин, иначе задача `bot_call getChatMember`). Собирает итоговую подпись. Ставит задачу `send_video`.
3. Воркер берёт файл из tmp-кэша или качает заново (формат до 50 МБ), вызывает `sendVideo`, возвращает `message_id` или код ошибки.
4. Ядро обновляет статус отправки и историю; при ошибке прав помечает цель неактивной.

### Апдейты бота

1. Ядро назначает одного подключённого воркера опрашивающим (`poll_updates=true` в конфиге).
2. Воркер делает long-poll `getUpdates` и пересылает каждый апдейт в ядро как есть (`BotUpdate.update_json`), подтверждая offset только после ack ядра.
3. Ядро обрабатывает апдейт и, если нужно ответить, ставит задачи `bot_call` (`sendMessage` и т. п.).

## Отказоустойчивость

- Задачи арендуются воркером на срок (`lease`); при обрыве стрима или истечении аренды задача возвращается в очередь. Повторы — до 2 раз для `retryable` ошибок.
- Если воркеров нет: резолв и подготовка файла из кэша работают; новые задачи ждут в очереди до 10 минут, затем `failed: worker_unavailable`.
- Воркер при потере ядра переподключается с экспоненциальным backoff (1 с → 60 с) и после 5 минут сообщает админу через бота.
